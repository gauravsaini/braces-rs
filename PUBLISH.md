## Binary distribution (what the package.json is wired for)

**Prebuilds-in-tarball.** `napi/package.json`'s `files` whitelist includes
`*.node`, and `napi/binding.js` (generated by @napi-rs/cli) loads a local
`./braces-rs.<platform>.node` file first. So whatever platform binaries
sit in `napi/` at publish time ship inside the single tarball, and the
loader picks the right one at require time.

Current state (verified by the dry run below): the tarball contains
**only** `braces-rs.linux-x64-gnu.node` (built on the Ubuntu box).
Publishing as-is would work ONLY for linux-x64-gnu users and fail to load
everywhere else. Before the first real publish, build the remaining
triples into `napi/`:

- defaults from the `napi.triples` config: `x86_64-pc-windows-msvc`,
  `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`,
  `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-gnu` …
- additional configured: `aarch64-apple-darwin`,
  `aarch64-unknown-linux-gnu`, `aarch64-unknown-linux-musl`

Tradeoff to know: each `.node` is ~0.77 MB, so a full matrix makes a
~5 MB tarball that every user downloads. The napi-rs standard
alternative — per-platform packages (`@braces-rs/<triple>` style
`optionalDependencies`, produced by `napi create-npm-dir` + `napi
artifacts`) — ships one binary per user and is the better long-term
route, but needs its own one-time npm org/scope setup and publishes
N+1 packages per release. The current wiring deliberately starts with
prebuilds-in-tarball; switch when download size matters.

## One-time maintainer steps before the first publish

1. `npm login` (the account that will own `braces-rs`) — credentials are
   the maintainer's; nothing in this repo can or should store them.
2. Confirm the unscoped name `braces-rs` is free on npm (first publish
   claims it).
3. Build the platform matrix into `napi/` (CI with one runner per OS, or
   cross builds where the toolchain allows):
   `npm run build` in `napi/` per platform
   (`node node_modules/@napi-rs/cli/scripts/index.js build --platform --release --js binding.js --dts binding.d.ts --cargo-cwd ../crates/braces-napi`).
   Note from the box build: invoke the CLI with a current Node (>= 14) —
   the box's snap `npm` is Node 10 and silently fails the copy step;
   also copy the built `.so` onto NTFS with plain `cp` (fs.copyfile
   EPERMs on the NTFS mount).
4. Re-run the gates on at least one platform build:
   `cargo test --release -p braces-core`,
   `node tools/check-conformance.js` (exit 0),
   `BRACES_REF=<micromatch-braces> node napi/test-multigroup.js`.
5. `npm publish` from `napi/` (add `--access public` — default for
   unscoped packages, but say it anyway).
